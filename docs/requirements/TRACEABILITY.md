## Review notes and known gaps

<a id="sec-001"></a>
### SEC-001 through SEC-003 — Actor provenance and authorization

Authentication establishes who is calling; authorization decides what that actor may do. The Console now derives its current actor from ASP.NET Core Identity through `ConsoleIdentitySession`, rather than trusting a freely selected participant ID. Domain services still validate the actor ID they receive, while the host is responsible for proving where that ID came from. The future REST API/web host must preserve the same boundary: derive the actor from authenticated Identity, ignore actor IDs supplied in request content, and add host-level forgery and unauthenticated-request tests.

<a id="rel-003"></a>
### REL-003 — Cycle prevention is host-local

The Console checks whether a proposed parent attachment would create a cycle, but the Graph boundary cannot currently guarantee this invariant by itself. A future Graph application service or graph-aware repository operation should enforce the rule for every host.

<a id="typ-004"></a>
### TYP-004 — Threaded comments are separate

Comment is no longer a seeded Graph node type. Atlas.Comments owns threaded comments. The older default-requested-type requirement is superseded by the separate Comments boundary.

<a id="aut-002"></a>
### AUT-002 — Node authorization is domain-enforced

Graph requires and validates the acting participant for every author-owned node mutation. The Console also marks author-only choices as disabled for other participants, but that presentation behavior is not the security boundary. The description workflow validates authorization before creating a replacement Content document so a rejected attempt cannot leave an orphaned document.

<a id="evt-002"></a>
### EVT-002 and NFR-002 — Demonstration versus durable messaging

The synchronous in-memory publisher demonstrates subscription and broadcast clearly. It does not survive a crash, cross a process boundary, retry delivery, or provide idempotency. Those are deliberately deferred until Atlas adopts durable transport.

<a id="vot-001"></a>
### VOT-001 through VOT-011 — Current SQL-backed voting

Node importance ratings and NodeReaction up/down votes support cast, change, undo, and summaries. SQL repository tests cover reconstitution, participant-target lookup, replacement, and deletion; SQL constraints enforce participant-target uniqueness. Production authentication, conflict recovery for competing first inserts, same-record lost-update handling, durable aggregates, and real-time service consistency remain open.

<a id="rea-001"></a>
### REA-005, REA-006, REA-008, and REA-009 — Remaining reaction integration

Graph models, SQL adapters, Console reaction flows, and NodeReaction voting are implemented. The broader moderator capability and visibility policies should still be verified against each requirement rather than inferred from SQL persistence.

## Suggested review order

1. Start with the five Graph fundamentals: GRA-001 through GRA-005.
2. Trace type and relationship rules through TYP-001 through REL-004.
3. Verify the Content reference and separate persistence through CON-001 and CON-002.
4. Walk through participant profile ownership using PAR-001, PAR-002, and AUT-001.
5. Review reusable-reaction ownership and workflows through REA-001 through REA-011.
6. Review the known architectural gaps: REL-003, EVT-002, the VOT requirement area, and NFR-002.

During manual review, change a status only when all acceptance criteria support the new value. Add a missing test link when evidence exists; do not treat a Console demonstration as automated verification.
